Why it matters

AI agents can now write code with nobody at the keyboard. Getting output is easy. Trusting it takes evidence. Did the tests run? Did the claim hold? Did anything sensitive slip out?

I wanted to answer two questions. Can a team of agents build real software on a schedule while a person keeps control of what ships? Can the work be made visible enough to check?

Who it's for

You have a company to run. You need capabilities that land, and clarity on what they'll take. I give you a high-confidence assessment of what it will take to build a product, feature or capability for your business: how long it will take, what it will cost, and how you can verify it works before it touches anything that matters. Then I build it.

This lab is the foundation of that business, Truehelm, an AI engineering team for small and medium-sized businesses. I built a small team of agents, run under clear rules with a person accountable for what ships. Here I took that model from zero to a team that ships. Sextant, the run monitor below, is what you get: a live view of where your project stands, what it costs, and the proof.

The walkthrough

Stop at any layer.

30 secondsThe idea

A scheduled team of AI agents built and tested a run-monitoring tool. I set the goal, the rules and the quality gates. No change merged without my go-ahead: I approved each one at first, and later a standing rule I set covered them (green checks and a passing review). The monitor is what they built.

2 minutesSextant, the run monitor

Truehelm Sextant is the monitoring and observability view over the team's work. It reads agent run logs and answers three questions, each with its source and sample size. Which skill fails most often? What does each scheduled run cost? Which claims carry no evidence? A number that was never measured shows as "not recorded", never a guess. It shows the build team's own run records, which are real, next to synthetic Claude Code and Codex logs. Each view labels which is which.

5 minutesThe system that built it

Several times a day, a lead agent wakes up in the cloud, reads the repo's state and picks the next task. It hands the work to specialist agents:

test engineerbuilderreviewerdesign criticred teamtutorsteward

Acceptance tests are written and frozen first. The builder writes code until they pass. A reviewer in a fresh context grades the change and must break one of its own checks to prove the tests can fail. Every change arrives as a draft pull request, and nothing merges without my go-ahead.

10 minutesThe guardrails

Agents that run unattended can rewrite their own rules. So the rule files are protected paths no agent branch may touch. The check that enforces this runs from the main branch, not from the pull request, so a change can't switch off its own guard. A scanner blocks secrets and personal data in every diff, and a red team attacks those guards. The red team and the reviewers found seven high-severity holes in the agents' own guardrails. One was a file name with a quote character that slipped past the scanner. Every fix came with its own tests, and most were written tests first.

What I kept, and what I delegated

The point was to find the line: what needs a person's judgment, and what can be handed to agents safely, with evidence that it worked.

I kept control of

  • The goal and the scope: three projects, with a phase plan and stop rules written before the build began
  • The operating model: who does what, what agents may never do, and the gates every change passes (drafted with AI, approved by me)
  • Product and design decisions, recorded with dates
  • Every merge decision, or the rule that made it

I delegated to agents

  • The code: all 462 commits on main were made by agents (95 of them under the account my agent sessions share)
  • The tests, written and frozen before each build
  • The reviews, red-team reports and run records

What I'd do differently

  • The first cycle costs real effort. Setting up the team and its rules took real work: 13 of 63 merged pull requests changed the rules rather than the product. Some of that was the initial setup, some was fixing what the red team found, and some was the system tuning itself.
  • I was the bottleneck. The team stops opening work when five pull requests are waiting or one is blocked on me, and that happened in 30 of its runs. The fix is clear examples of the quality bar, so agents can make the revisions themselves and first-pass work improves without a person in every review.
